## Phase 1 — the guardrail · **SHIPPED TO main** (`5eb2ccce`)

`eslint-rules/no-hardcoded-jsx-text.js` fails the build on a user-facing string that never reaches
`t()` — text children of text components, user-facing string props, and Alert/Toast arguments.
Non-user-facing literals (testIDs, icon names, style keys, hrefs) are allowlisted **by name in one
file**, never by per-file disable comments, because a disable comment is invisible at review and
permanent by default.

Wired into **both** gates, which is the point: `.github/workflows/i18n-guard.yml` on push (every
branch) and `.githooks/pre-commit`. The existing ota-guard runs on `pull_request` only, and its own
header records the cost — work here goes straight to main, so a PR-only guard never fires.

**It lints changed LINES, not changed files.** The first version linted whole staged files and
blocked a prose-only comment deletion by reporting 39 pre-existing violations in the same file. That
is how a gate gets `--no-verify`'d within a day. `scripts/i18n-changed-lines.mjs` is shared by the
hook and CI so the two cannot disagree about what counts as new.

Break-tested in both directions: a new literal blocks a commit (`git commit` exits 1, HEAD does not
move), and a comment-only edit to a legacy file passes.

`en` is complete: the codemod wrote every English value as it removed the literal, so the app renders
identically in English. **es/zh are missing the 1,910 new keys** — i18next falls back to `en`, so
those screens look exactly as they did before. No regression, no gain.

**ja and ko do not exist.** There is no translation API key available in this environment

### Golf vocabulary for human review — 287 strings, not buried

287 of the 2,088 English strings contain golf terms machine translation reliably gets wrong. Full
per-term key list: `scripts/codemod/.i18n-golfterms.json`.

| count | category | examples |
|---|---|---|
| 80 | course | tee, fairway, green, carry, layup, pin, bunker, dogleg |
| 74 | equipment | club, ball, bag, driver, wedge, hybrid, loft |
| 63 | scoring | handicap, index, par, putts, stroke, GIR, vs par |
| 58 | swing | tempo, backswing, contact, impact, over the top |
| 7 | shot shape | draw, fade, hook, slice, thin, fat, chunk |
| 5 | rules | penalty, drop, relief, stroke and distance |

Most frequent: `tempo` (30), `club` (26), `ball` (23), `handicap` (21), `tee` (16), `carry` (15).

**These are where a Japanese player judges the app in the first ten seconds.** Japanese golf uses a
mix of katakana loanwords (ドライバー, バンカー, パー) and native terms, and the register differs
between a scorecard label and a caddie speaking. Korean likewise. Machine output will be
grammatically fine and idiomatically wrong.

## Phase 4 — voice path · **PARTIALLY DONE**

**STT — done.** `api/transcribe.ts:25` now maps `ja: 'ja'` and `ko: 'ko'` for Deepgram nova-2
(plain two-letter, unlike Chinese which needs `zh-CN`). An unknown code still falls back to `en`.

**Kevin's system prompt — the premise was wrong, and it mattered.** It is *not* locale-agnostic.
`LANG_ENFORCEMENT` (`api/kevin.ts:841`) is a hardcoded map that held only `es` and `zh`, read as
`LANG_ENFORCEMENT[language] ?? ''` — so a locale with no entry gets an **empty rule** and the brain
answers in English with nothing reporting a problem. Adding a language to the app without adding it
here would have looked like it worked until someone spoke Japanese. `ja` and `ko` entries added, each
specifying a spoken register (natural spoken Japanese; 해요체 for Korean) rather than textbook
formality — a caddie talks to a player between shots.

**Filler cache key — the premise was also wrong, in the app's favour.** `voiceHash()`
(`services/fillerLibrary.ts:47`) returns `` `${persona}_${language}_v5` ``. **Locale has been in the
key all along**; it was never broken for es. The actual es breakage is two other things, both still
open: `constants/fillerPhrases.ts` holds **58 English-only phrases**, and `/api/voice` **discards**
the `language` it is sent (`api/voice.ts:85`, destructured and never referenced again). So the `es`
cache slot is correctly named and full of English audio.

**Audio generation — measured, not generated.** Reported before doing anything, as asked:

| set | files per locale | size per locale | ja + ko |
|---|---|---|---|
| `assets/audio/greetings/` (launch) | 36 | 1.99 MB | 3.98 MB |
| `assets/audio/greetings_local/` (mic-open) | 15 | 0.48 MB | 0.96 MB |
| **bundled total** | **51** | **2.46 MB** | **4.93 MB** |

**4.93 MB — under the 15 MB ceiling.** The 58 filler phrases add **zero** bundle size:
`fillerLibrary` generates them on-device at first launch and caches them. They cost download time and
device storage, not app size. Not generated: no TTS key here, and the greeting text must be
translated first (Phase 3).

## Phase 5 — verification · **NOT STARTED**

Blocked behind Phase 3. The agreed approach is a locale-render harness rather than screenshots —
render each first-session screen under `i18n.language = 'ja'` / `'ko'` and assert no Latin-script
leakage outside an allowlist (brand names, GIR, PAR). It catches English leakage the way a screenshot
would, runs in CI forever, and needs no device. Store screenshots stay a manual pass on a real phone.

## Swing Analysis Orchestrator — PARKED until after App Store submission (Tim, 2026-09-06)

**Tim's call:** "park it until after we get through app stores, then we can do things like this that
are cleaner pipelines and diagnostics."

**The idea.** Wrap swing analysis in one engine that owns the STAGE ORDER, the way
`services/courseDataOrchestrator.ts` already does for courses. Today that order is an emergent
property of React effects rather than a decision anything makes, which is how three separate defects
got in on 2026-09-06:

- `bodyBoundsFromPose` lived in `app/swinglab/smartmotion.tsx` — a SCREEN — so the pose pipeline
  could not reach it and ran full-frame forever.
- The club-arc stage runs in a `useEffect` with `isPlaying` in its deps, so a play/pause toggle
  re-fired a PAID vision call on a swing already answered.
- `roiFromBodyBounds` was wired to the club path but not to pose, because nothing owned the question
  "who gets the crop".

**The stages, in their real dependency order:**

| # | stage   | produces    | notes |
|---|---------|-------------|-------|
| 1 | locate  | window      | where the swing is in the clip |
| 2 | anchor  | impactMs    | acoustic strike, else a fraction (must stay distinguishable) |
| 3 | frame   | roi         | **feeds 4 AND 6** — this is the edge that kept getting missed |
| 4 | pose    | poseFrames  | body at the anchor times |
| 5 | metrics | tempo, faults | derived from pose |
| 6 | club/ball | arc       | needs roi + window + anchor |

**Why it is worth doing (and what it is NOT).** It buys ~nothing in analysis QUALITY directly. What
it buys: one run per `(clip, window)`, cached; work never repeated; and a per-stage status so the log
says "stage 4 partial, stage 6 skipped — no roi" instead of `points: 0`. That is the same object that
would later become an analysis API.

**Ship vector: OTA.** Pure TypeScript, no native surface, so `.github/workflows/ota-guard.yml` passes
it. And it is covered by the Layer 0 kill switches — `swing_analysis` and `cage_capture` — so a bad
refactor can be pulled in seconds without a store build. That pairing is the reason it is safe to do
this one OTA at all.

**Do the cheap wins FIRST — they dominate.** Ranked honestly:
1. **60fps capture.** At 30fps the clubhead travels over a metre between frames; no algorithm
   recovers a club that is not in the picture. Tim had the setting wrong on the 2026-09-06 upload.
2. **The pose crop** (shipped 2026-09-06). Golfer went from ~25% of frame height to filling it.
3. **Closer framing / less sky.**
4. The orchestrator.

Measure 1-3 before building 4. If 60fps + crop gets the club trace working, this is cleanup on a
schedule of your choosing; if it does not, the new `pose_partial_coverage` log (missed / nudged /
zoomed / poseSpanMs) will finally say why.

## PIN POSITION — **BUILT 2026-09-13 (Option A).** Kept here for the reasoning; the code is live.

> Implemented as described below, with one correction that came from Tim mid-build: "but aren't there
> general pin position rules that give a good estimate?" There are, and they replaced the model scoped
> here. See `services/pinPosition.ts` — a pin sits an INSET FROM THE EDGE (greenkeeping convention, USGA
> guidance ≥4 paces; 5 used), not a FRACTION of green depth. The edge rule self-corrects for green size
> the way pin setting actually does: a 44-yard green gets a genuinely deep back pin (+17), a 12-yard green
> barely moves (+1). A fraction gets both wrong in opposite directions.
>
> Files: `services/pinPosition.ts` (the rule), `store/roundStore.ts` (`pinPosition` / `pinDeclared`,
> persisted but cleared at round start), `services/yardageResolver.ts` (applied ONCE, for all 13
> consumers), `app/(tabs)/play.tsx` (the 3×3 grid), `services/caddieRequestBody.ts` + `api/kevin.ts` (the
> SIDE, which no yardage can carry). Guarded by
> `__tests__/regression/the-pin-moves-every-yardage-at-once.test.ts`, 14/14 mutations caught.
>
> Not built, deliberately: B (per-hole capture). Revisit after a real round — the open question is
> whether a per-hole prompt earns its interruption.

### Original scope, for the record

> *"what would it take to have input for pin position? I know the numbers change but back right, left,
> front right, front left that could be entered by the user on the play tab? This would have to be tied
> to green logic which is why i disturbed you… to be useful would have to pop like cart/walk selection"*

**Verified first: nothing models a pin position today.** `pinPosition` / `flagPosition` /
`pinQuadrant` appear nowhere in the codebase. This is a build, not a wire.

### Why it is cheaper than it looks

Three things already exist that would otherwise be the hard parts:

1. **The green already has DEPTH.** `ResolvedYardage` carries `front`, `value` (middle) and `back`, and
   `is_fallback` says whether they are real. So a quadrant converts to YARDS from measured green depth
   rather than a guessed constant — "back" is `middle + k × (back − middle)`, not "+8 because pins are
   usually 8 back".
2. **`services/yardageResolver` is the single owner with 13 consumers** (the caddie payload, the watch
   bridge, SmartFinder, the cockpit, voice readback, queryStatusHandler, shotTracking…). A depth offset
   applied THERE reaches every surface with no per-surface work. This is the payoff from the 09-10
   yardage unification.
3. **The prominent-chip pattern exists**, built 2026-09-13 for walking/cart: `app/(tabs)/play.tsx`
   around the `transportBtn` row — half-width targets, 24px `AppIcon`, `accessibilityState.selected`.
   And `roundStore.transportDeclared` is the pattern for "did the player actually choose, or is this
   just the default?", which a pin needs for exactly the same reason.

### What it would take

- **Model** — `roundStore`: `pinPosition: { depth: 'front' | 'middle' | 'back'; side: 'left' | 'center' | 'right' } | null`
  plus `pinDeclared: boolean`. Nine cells, which is also the clearest possible picture of a green: a
  3×3 grid reads as the green itself, where four named corners read as a word problem.
- **Distance** — DEPTH only, in `yardageResolver`, and **only when `front`/`back` are real and
  `is_fallback` is false**. When they are not, decline and keep middle. Guessing a pin offset on a
  fallback green is the fabrication this codebase exists to refuse.
- **Aim** — SIDE is not a distance. It goes to `caddieDecision` / `holePlan` as a bias and into
  `caddieRequestBody` so the caddie can say "pin's back right — favour the left half, long is dead".
- **Entry** — the Play-tab chip row at setup, exactly as he describes. This is not a compromise: real
  pin sheets are set per DAY, so "today's pins are back" is how the information actually arrives.
- **Optional later** — a per-hole override, and feeding the declared quadrant into `greenHeat` so the
  putting record learns which quadrant costs him strokes. Neither is needed for v1 of this.

### The honest caveats, to decide with

- It is only as good as the entry, and a wrong pin makes every yardage on the hole wrong — which is
  worse than no pin. So `pinDeclared` must gate it and the caddie must be able to say where the number
  came from, the same way `yardageSource` already labels GPS vs card.
- A round-level pin is a generalisation. On a course that mixes pins it will be wrong on some holes,
  so the adjustment should stay modest (a fraction of depth, not the full front/back spread).

### Decision — **A, chosen by Tim 2026-09-13**

**A. Round-level pin on the Play tab** — the scope above. Contained, and it matches how pin sheets
actually arrive: set per day, not per hole. This is the next build.

B (per-hole capture, prompted at hole advance) is NOT rejected — it is A plus a capture UX, and A's
model and plumbing are the same either way. Revisit once A has been used on a real round, because the
open question is whether a per-hole prompt earns its interruption.

## Putt read — the ground-level view ("second level"), deferred 2026-09-13

Tim, while the grounded slope read was being built: *"For a put when it super tough, could there be a
second level placing phone on the ground and it sees the terrain lie to the pin clearly? Just curious."*

**The idea is sound and the physics is real.** At standing height a 2% slope over 20 ft — about five
inches of rise — is foreshortened to almost nothing. An inch off the deck, that same rise stands up
against the backdrop. It is exactly why a player crouches behind the ball, and a vision model reading
that frame has far more signal to work with than one shot from chest height.

**Why it is NOT a free addition to what shipped today.** The grounded slope read has the phone lying
flat, screen up — so the rear camera is pointing at the grass. Good inclinometer, no view. To see down
the line the phone has to be STOOD on its bottom edge. Two different poses; one phone.

**What makes it worth building anyway.** A phone resting on the green has no hand tremor — and hand
tremor (±2-3°) is the entire reason the AIMED read was untrustworthy and had to be given a deadband.
A stood-up phone is the aimed read with its dominant error source removed, plus the grazing-angle
frame. That is a genuinely better instrument than either pose alone.

**Open questions to settle before building it**
- Standing a phone on a green is precarious and slow. Does it earn the fiddle on a real putt, or is it
  only for the "super tough" read Tim scoped it to? Ship it as an explicit extra step, never a default.
- A phone stood on its edge reads the surface tilt where it stands *plus* however it leans. Separating
  those two needs care — the same discipline `readGroundSlope` applies, and the same refusal to invent
  a convention that has not been verified on a device.
- Whether the vision step should attempt a slope call from the grazing frame at all, or stay a
  qualitative "the ground falls away left beyond the midpoint" description. Leaning qualitative: it is
  honest about what a picture can support, and the inclinometer already owns the number.

Not built today. What shipped is the flat-pose inclinometer (`readGroundSlope`, both orientations),
its confidence model, and the flagstick/hole vision cross-check on the frame captured at read time.

## Green fees: Vet / PGA / public-service discounts, deferred 2026-09-13

Tim, heading out to test: *"Im gonna play Echo Hills in Hemet a few times since its $12 for Vets (in
future versions we need to find Vet and PGA discounts/Public Service etc."*

**The ask.** Surface the discounts a player actually qualifies for when they are looking at a course —
veteran/military, PGA member, first responder, senior, student, junior, twilight, resident rates.

**Why it fits.** The app already resolves courses (`courseNameResolver`, `courseDataOrchestrator`) and
already holds a player profile. Eligibility is a small, stable, PROFILE fact — the kind that is set once
and is true for years — and the payoff is real money on every round. $12 versus a $45 rack rate is the
difference between playing twice a week and twice a month.

**The honest problem, and it is the whole problem.** Discount rates are not in any golf course API we
use. They live on club websites, on Golf Now, in a phone call to the pro shop, and they change without
notice. So the failure mode is the one this app keeps having to avoid: confidently telling a player a
rate that is wrong, which is worse than saying nothing — it sends them to a course expecting $12 and
they pay $45.

**Shape it would have to take**
- A profile field for eligibility (multi-select, set once in Settings), which is cheap and safe.
- The caddie ABLE TO BE ASKED — "do they do a vet rate here?" — answering from whatever is actually
  known, and saying plainly when it is not known rather than guessing. This half is worth having even
  with no rate data at all, because "call the pro shop and ask for the veteran rate, most courses in
  this area do one" is genuinely useful and is not a fabricated number.
- Any actual RATE shown must carry its source and date, or not be shown. No scraped number presented as
  today's price.

**Not built.** The eligibility profile field is the cheap half and could ship any time; the rate data is
the hard half and should not ship as a guess.
